# 跨雲比較

`compare` 模式的步驟 5 用。目標：AWS 與 GCP 在同樣的條件下比。

## 公平性規則

1. **同一組使用量假設。** 兩朵雲用同一張使用量表、同樣的三情境。
2. **同等級的區域。** 預設都選離使用者最近、且所需服務都有提供的區域。台灣使用者先查兩朵雲的台灣區域；某服務在台灣區域沒有，兩邊都記下替代區域與延遲影響。
3. **同等級的託管程度。** 託管對託管、自架對自架。不要拿 AWS 的 VM 自架資料庫比 GCP 的全託管資料庫。
4. **同樣的可用性。** 單可用區對單可用區，多可用區對多可用區。
5. **同樣的計價方式。** 主比較用隨需（on-demand）牌價。承諾折扣、Spot、credits 另列一欄，不混進主比較。
6. **同樣的費用類別。** 兩邊都跑完 cost-estimation.md 的〈常漏的費用〉，一邊算了 NAT，另一邊也要算或寫「不需要」。
7. **同一天的價格。** 兩邊價格的查詢日期要相同或相近，寫在報告開頭。
8. **無法對齊的差異要寫出來。** 例如計費粒度不同（每秒 vs 每小時）、免費額度不同、某服務只有一邊有。列在矩陣下方的〈不可比的差異〉。

## 加權評分（選用）

只在使用者要求，或兩邊差異很接近時用：

- 權重來自步驟 1 使用者給的優先順序，不要自己訂。
- 權重與分數寫進報告，讓使用者能改權重重算。
- 分數計算用腳本。

## 不可比的差異

矩陣下方列出：

- 只有一邊有的服務或功能。
- 計費粒度、免費額度、最低費用的差異。
- 某邊有「未驗證」項目，導致該格無法比較。

## 結論寫法

- 先寫在使用者的限制下選哪一邊，再寫翻盤條件，例如「若團隊已熟悉 Kubernetes，結論改為 ○○」。
- 差異在誤差內（例如月費差距小於 10%，且其他面向相當）：明說「兩邊都可行」，改由團隊熟悉度或既有帳號決定。
