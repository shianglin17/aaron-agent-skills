# 檢查、審查、發布、維護

流程步驟 4–7 照這份。

## 檢查（步驟 4）

### 內容檢查

```sh
python3 scripts/check_site.py <站的資料夾> --repo <repo>
```

| 檢查 | 失敗時 |
|---|---|
| 圖上每個 `data-key` 都有面板資料；每筆面板資料都在圖上 | 補資料或刪節點 |
| `lede` 不超過 3 句、120 字、3 個數字；`kv` 不超過 3 項 | 刪減，或移進 `details` |
| 每個 SVG 有 `<title>`、`<desc>` | 補上 |
| 每頁都在 `PAGES`，`data-current` 對得上 | 改 `shared.js` |
| 全站頁尾是同一個 commit，且 repo 有這個 commit | 換成目前的 commit |
| `src` 的檔案存在，行號沒超過檔尾 | 重新核對行號 |
| `kv` 的 `code` 常數值跟程式相同 | 以程式為準改頁面 |
| 同一個數字出現在多頁（只警告） | 留在最主要的頁，其他頁連過去 |

- 行號存在不等於指對地方。每次更新都打開檔案，確認該行是說明的那段程式。
- 站的結構跟骨架不同時，照上表改寫檢查腳本，不要跳過。

### 瀏覽器檢查

```sh
uv run scripts/smoke.py <站的資料夾>
```

- 寬度 390、1280，淺色與深色，共 4 種。
- 沒有 JS 錯誤、沒有 console error、沒有橫向捲動。
- 點過每個節點與連線，面板都有內容；鍵盤能選取。
- 相對連結都指到存在的檔案；nav、`summary` 至少 44px 高。
- 用 Playwright 這類 headless 瀏覽器跑；不要操作使用者自己的瀏覽器。

## 審查（步驟 5）

- 派獨立 reviewer：只給頁面和原始文件（程式碼、決策文件），不給製作說明。
- 每位 reviewer 都查三件事：
  - 對不對：數字、行號、流程跟程式一致。
  - 有沒有漏：決策文件的重要結論都在頁面上，或確定不放。
  - 讀者看不看得懂：讀完每頁，能回答該頁的問題。
- 審兩次，視角不同：

| 視角 | 重點 |
|---|---|
| 工程師 | 流程與程式碼一致、行號正確、邊界情況有沒有寫錯 |
| 主管 | 每頁的問題有沒有答到、術語看不看得懂、數字有沒有出處 |

- reviewer 的意見照 `verify-review-findings` 逐條核實後再改。

## 發布（步驟 6）

發布成 claude.ai artifact 時：

- [ ] 第一次發布：主頁用 `file_path`，其他頁與共用檔用 `files`。
- [ ] 之後每次都發布到同一個網址；不另開新網址。
- [ ] 發布前先讀線上現版，把線上的修改合併進來。
- [ ] 發布前整份讀過每個檔案；檔案大就派 subagent 分頁讀。
- [ ] 照全域規則逐行掃個資、帳密、本機路徑、session ID。
- [ ] 發布後讀回每一頁，跟本機檔案比對，並點過每個 nav 連結。
- [ ] 在線上版重跑瀏覽器檢查的 4 種組合。

## 維護（步驟 7）

程式或資料模型改了：

- [ ] 列出受影響的頁：改到的檔案出現在哪些 `src`、`code`。
- [ ] 更新這些頁的圖、面板資料、數字（數字附新的查詢日期）。
- [ ] 頁尾換成新的 commit，重新核對全站行號。
- [ ] 跑內容檢查與瀏覽器檢查。
- [ ] 改動大（新增頁、圖的結構變了）：再審查一次。
- [ ] 照〈發布〉發布到同一個網址。
